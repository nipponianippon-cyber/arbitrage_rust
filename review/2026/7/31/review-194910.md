## 指摘事項

### 1. [High] Meteora-DLMM の LbPair デコードと価格式が未検証の仮実装になっている

- 種別: バグ
- 重大度: High
- 場所: `src/dex/meteora/meteora_amm.rs:9`
- 内容: `STATUS_OFFSET`、`ACTIVE_ID_OFFSET`、`TOKEN_X_MINT_OFFSET` などの固定 offset と、`active_bin_price` の `step.powi(active_id) * decimal_adjustment` が公式 SDK または fixture で裏取りされていません。コード内にも「SDK検証前の最小実装」と明記されています。
- 影響: LbPair の実レイアウトと offset がずれている場合、mint、decimals、fee、active_id を誤読します。mint だけ偶然一致しない場合は取得失敗になりますが、誤読値が成立した場合は間違った `USDC per SOL` 価格を正常値として通知・保存します。
- 修正案: Meteora-DLMM の公式 SDK または既存 crate の LbPair 型定義に合わせて decode 層を作り直し、実アカウント fixture または SDK 由来の固定バイナリで `active_id`、`bin_step`、token mint、decimals、fee、status、価格を検証する単体テストを追加してください。`f64` での指数計算は丸め誤差が出るため、SDK の quote/price ロジックに寄せるか、少なくとも `Decimal` へ変換する前に期待値テストで許容誤差を固定してください。
- 確認方法: Meteora-DLMM SOL/USDC の既知 LbPair fixture を使い、`decode_pool_meta` と `decode_price` が SDK の値と一致することを `cargo test` で確認します。

### 2. [Medium] 監視サイクルの成功条件が `prices.len() == 3` に固定され、重複 DEX 設定で誤判定する

- 種別: バグ
- 重大度: Medium
- 場所: `src/runner.rs:90`
- 内容: `validate_config` は Raydium、Orca、Meteora-DLMM が含まれることだけを確認しており、同じ DEX の有効プール重複を禁止していません。一方 `run_once` は成功価格数がちょうど 3 件の場合だけ価格差計算に進みます。
- 影響: 例えば Raydium が 2 件、Orca が 1 件、Meteora-DLMM が 1 件の設定では、全必須 DEX の価格取得に成功しても `prices.len() == 4` になり、価格差計算がスキップされます。逆に同一 DEX 重複を許す設計なら、どの 3 件を比較するかが曖昧です。
- 修正案: 初期実装を SOL/USDC の 3 DEX 各 1 プールに限定するなら、`validate_config` で有効プールを DEX ごとに 1 件だけ許可してください。複数プールを将来許可するなら、`run_once` は `DexKind` ごとに対象価格を選別し、`calculate_all_spreads` へ渡す集合を明示してください。
- 確認方法: Raydium 重複設定を持つ `AppConfig` の単体テストを追加し、設定エラーになること、または意図した 3 DEX のみで比較されることを確認します。

### 3. [Medium] `price_spreads` と `price_spread_pairs` が併存し、保存先の意味が分かれたままになっている

- 種別: 設計
- 重大度: Medium
- 場所: `src/storage.rs:42`
- 内容: 旧 Raydium/Orca 専用の `price_spreads` と、新しい DEX ペア汎用の `price_spread_pairs` が併存しています。`insert_price_spread` は全 spread を `price_spread_pairs` に保存し、Raydium vs Orca の場合だけ追加で `price_spreads` にも保存します。
- 影響: 同じ比較が 2 つのテーブルに重複保存されるため、後続の分析や運用確認でどちらを正と見るべきか曖昧になります。将来の migration でも、旧テーブルだけを見るコードが新しい Meteora 比較を見落とす可能性があります。
- 修正案: 現行アプリの正規保存先を `price_spread_pairs` に一本化し、`price_spreads` は互換用 legacy として明示的に分離してください。可能なら `insert_legacy_raydium_orca_spread` のような名前に分け、呼び出し側で必要時だけ使う形にすると意図が明確になります。新規の読み取り・分析コードは `price_spread_pairs` だけを参照する方針をコメントまたは migration 名で残してください。
- 確認方法: SQLite 初期化テストを追加し、3 DEX 比較時に `price_spread_pairs` へ 3 行保存されること、legacy テーブルへの保存有無が仕様通りであることを確認します。
